## 1. Architecture audit — stage by stage

**Stream Manager / video ingestion — PARTIAL.** There's no persistent "stream manager" process (no RTSP/live-stream handling, no per-camera worker loop). Ingestion is file-based: `pipeline.py` and `demo/visual_pipeline.py` both take a video file (or a camera-folder-of-clips in the demo case) and process it start-to-finish. That's fine for a video-upload demo mode but is not a live CCTV stream manager. Your plan's item 14 ("Demo Mode: upload CCTV video") is actually the natural fit for the current architecture — lean into that rather than building live RTSP ingestion, which is a much bigger lift SIH judges won't expect working end-to-end.

**Vehicle Detection + Tracking — DONE.** `detection/vehicle_detector.py` wraps a stock YOLOv8 (COCO classes car/truck/bus/motorcycle) with ByteTrack, always returns a `track_id`. No training needed, works out of the box. This matches your plan's diagram exactly.

**Plate Detection — DONE, trained.** `detection/detect_plates.py` + a custom-trained detector. Two weight artifacts exist: `models/best_plate_detector.pt` and `models/best.onnx`; the previous audit flagged these as needing reconciliation (are both current, or is one stale?) — that's still open. `pipeline.py`'s v2/v3 rewrite fixed a real bug: plate detection now runs *inside* the vehicle crop (not the whole frame), which is both more accurate and is exactly the flow your diagram specifies.

**OCR — PARTIAL, and the accuracy question is unresolved** (see section 0). Architecturally the pipeline is complete and matches your item-2 diagram almost exactly: plate crop → LPRNet (primary) + PaddleOCR (secondary) → `vote_plate_text()` multi-frame voting → `plate_normalizer`/Indian format validation → confidence score. What's missing against your plan: no condition-wise breakdown (daylight/low-light/blur/angled/rain) exists anywhere — `docs/OCR_EVALUATION.md` explicitly says "not measured... do not invent condition-wise percentages." Building that table is real, uncredited work, not a rerun of what exists.

**Multi-frame voting — DONE.** `recognition/ocr_reader.vote_plate_text()` is wired into both `pipeline.py` paths, confirmed by the README's own changelog notes.

**Event Queue — NOT REALLY THERE.** This is the honest gap behind your item 3 (trajectory latency). `docker-compose.yml` defines a Redis service and `backend/app/core/config.py` has Redis host/port settings, but the previous audit found "actual event queue implementation appears limited... dashboards report Redis status as connected in code paths that look like demo-friendly stubs." There is a WebSocket manager (`backend/app/websocket/manager.py`) which is a reasonable near-real-time push mechanism for the frontend, but that's push-to-client, not an ingestion event queue. Today, the pipeline is a batch script: run a video through, write to SQLite, and only then do trajectory/analytics/alerts read from the DB. If your "780 sec trajectory latency" number came from timing that batch path end-to-end, that's consistent with a synchronous, non-streaming design — I did not find a script in the current tree that reproduces that specific 780s figure (the standalone latency-measurement script referenced in the old pre-cleanup audit isn't in the repo anymore), so I can't independently confirm it, but the architecture explains why it would be large: nothing is incremental.

**Event Database — DONE**, and it's real, not a stub: SQLite dev store (`database/observation_store.py`, `camera_store.py`, `blacklist_store.py`, `alert_store.py`, `vehicle_registry.py`) plus a full Alembic-migrated Postgres/PostGIS path under `backend/`. Source-tagging exists (`record["data_source"] = "REAL_INFERENCE"`), which is exactly the "never let seed data look like live evidence" requirement in your plan item 10 — that discipline is already in the code, not just aspirational.

**Trajectory Engine — DONE, greedy not optimal.** `intelligence/trajectory.py` builds multi-camera trajectories using `intelligence/fusion.py`'s combined plate + appearance + temporal + spatial score. README states plainly it's "greedy best-score-first, not Hungarian algorithm" — an honest, reasonable scope call, not a bug. The appearance signal was previously silently dead (fusion always scored 0 for it) and was fixed — worth knowing so nobody "fixes" it back.

**Distance/Speed — DONE, but road-graph values are hand-estimated**, not computed from GPS via Haversine dynamically, nor road-network-aware. `network/camera_network.py` (16.8KB) defines the topology and `ROAD_GRAPH`/`CAMERA_RELIABILITY` constants — README says explicitly these are "manual placeholder estimates... replace with your actual filming layout." Your plan's item 4 (Haversine-based distance) is a real, scoped task: swap the manual constants for a computed Haversine distance using each camera's actual lat/lon, which are already stored per-camera.

**Camera Network / Topology — DONE.** `network/camera_network.py` defines a real multi-camera graph (the compliance doc references a "7-camera Coimbatore network"), consumed by fusion/trajectory. This is further along than your plan implies — item 5 is largely built, not greenfield.

**Suspicious Route Detection — DONE.** `intelligence/alerts.py` + `intelligence/anomaly_scoring.py` implement impossible-travel-time and vehicle-class-mismatch anomalies; `SIH_REQUIREMENT_MATRIX.md` shows real detected anomalies (2 vehicle-class mismatches, 1 repeated-camera sighting) from actual DB observations, not fabricated examples. `intelligence/route_hypothesis.py` and `intelligence/spatio_temporal.py` add further reasoning. This directly satisfies your item 6, including the "call it route anomaly, not criminal vehicle" naming convention — the code already avoids that framing.

**Congestion/Bottleneck — DONE at the analytics layer, frontend page exists (`CongestionPage.tsx`, freshly modified), but I did not find a dedicated `congestion` FastAPI router** among `backend/app/api/v1/*` — the closest is `analytics.py`. Worth confirming during Phase 1 whether `CongestionPage.tsx` calls a real congestion endpoint or is calling into the general analytics endpoint (or worse, holding placeholder data) — I did not read that file's contents, so treat this as a verify item, not a confirmed problem.

**Traffic Intelligence / Analytics — DONE.** `analytics/analytics.py` (17.8KB) computes density, camera flow, OD patterns, congestion, route density, temporal trends, corridor speed — all from real observations, per the compliance doc's numbers (9.8 km/h average speed, CAM_04 busiest at 26 vehicles, etc.). A FastAPI `analytics.py` router exposes this.

**Blacklist / Alert Engine — DONE.** `database/blacklist_store.py`, `intelligence/alerts.py`, fuzzy plate matching at 85% similarity threshold, a dedicated alert demo (`demo/run_alert_demo.py`) that seeds 5 blacklisted vehicles and produces 4 real alerts end-to-end. Frontend `AlertsPage.tsx` and `AdminPage.tsx` (blacklist management) both exist.

**Event Database hygiene (real vs demo) — DONE**, addressed above under Event Database; this was a specific worry in your plan (item 10) and it's already handled with a `source`/`data_source` field distinguishing `REAL_INFERENCE` from seeded/demo data.

**GIS Map — DONE.** `gis/gis_map.py` (Folium: camera markers, trajectories, heatmap, OD flow) plus a React `GISPage.tsx` (15KB, the largest page after RouteAnomaly/Congestion, suggesting real map logic, not a stub).

**FastAPI Backend — DONE, and substantially production-shaped.** Full `app/` structure: `api/v1/*` routers, `core/` (config, database, security, logging, monitoring, **cache**), `models/` (SQLAlchemy: alert, audit_log, camera, observation, road_network, user, vehicle), `schemas/` (Pydantic), `services/` (alert, analytics, audit, camera, vehicle), `websocket/manager.py`. Alembic migrations exist for cameras, observations, vehicles, alerts, PostGIS extensions, road network — six migrations, meaning schema evolution is already being managed properly, not just `create_all()`. This is well beyond "create clean APIs" as a to-do; it's mostly done. Your plan's item 12 list of endpoints (`/api/cameras`, `/api/vehicles/{plate}/trajectory`, etc.) already exists in some form — verify exact paths against `app/api/v1/*.py` rather than re-speccing them from scratch.

**Product UI — DONE, further than "Streamlit → product-style."** The React frontend already has the sidebar/dashboard/map shape your item 13 mockup describes, across 11 pages, with auth (`LoginPage.tsx`), 404 handling, and role-aware admin. The redesign task is smaller than framed: it's "audit and polish an existing React app," not "build a product UI from a Streamlit prototype."

**Demo Mode — PARTIAL.** `demo/visual_pipeline.py`, `demo/camera_simulator.py`, `demo/seed_demo_data.py`, `demo/run_alert_demo.py`, `demo/annotate.py` all exist and are real (not stubs — camera-folder-as-video simulation, real YOLO+OCR run, DB writes). The README describes exactly the "upload video → process → see trajectory" flow you want in item 14, tied to the (now-removed) Streamlit dashboard's "Live/Video Ingestion" tab. **This is the biggest concrete casualty of the dashboard removal**: that tab doesn't exist in the React frontend yet (I didn't find an upload-and-process UI among the 11 pages listed). **Security / RBAC — PARTIAL.** JWT + password hashing exist (`backend/app/core/security.py`), role fields exist on the user model, admin endpoints exist, `backend/seed_db.py` creates a default admin. What I can't confirm without reading the route bodies is whether every sensitive endpoint actually enforces role checks or just requires *any* authenticated user — flag as verify, not confirmed-missing.

**Tests — DONE, and substantial.** `backend/tests/` (auth, vehicles, alerts + conftest), root `tests/` (18 files covering camera network, analytics, anomaly scoring, database, day-by-day pipeline milestones, edge cases, OCR evaluation, plate normalization, route hypothesis, spatio-temporal, vehicle dedup), `integration_tests/` (multi-frame tracking, real OCR, sample PNG, video detection). `SIH_REQUIREMENT_MATRIX.md` claims 193/193 passing as of 2026-09-05 — that predates today's edits to `CongestionPage.tsx`/`RouteAnomalyPage.tsx`/`VehiclesPage.tsx`/`config.py`/`pipeline.py` (all modified today, per file timestamps), so that pass count needs re-confirming, not assumed current.
